## The Core Idea: Typed, Three-Way Step Outcomes

Every step declares its own error type. Zart distinguishes between:

- **`Ok(T)`** — the step succeeded.
- **`BusinessErr(E)`** — the step's own error type (e.g., `PaymentError::InsufficientFunds`). These are **business decisions**.
- **`ZartErr(ZartStepError)`** — a framework-level failure (retry exhausted, step timed out). These are **infrastructure problems**.

<Tabs syncKey="sdk">
<TabItem label="Rust">

```rust
pub enum StepOutcome<T, E> {
    Ok(T),              // success
    BusinessErr(E),     // the step's own error — a business decision
    ZartErr(ZartStepError),  // framework failure (retry exhausted, timeout)
}
```

</TabItem>
<TabItem label="Python">

```python
# zart.StepOutcome (returned by await zart.step(...))
# - outcome.is_ok           -> outcome.value
# - outcome.is_business_err -> outcome.error
# - outcome.is_zart_err     -> outcome.error (ZartError)
```

</TabItem>
<TabItem label="TypeScript">

```ts
// StepOutcome<A> (returned by yield* Zart.outcome(...))
export type StepOutcome<A = unknown> =
  | { readonly _tag: "ok"; readonly value: A }
  | { readonly _tag: "business_err"; readonly errorType: string; readonly message: string; readonly data?: unknown }
  | { readonly _tag: "zart_err"; readonly error: unknown };
```

</TabItem>
</Tabs>

This distinction matters because business errors deserve specific handling — insufficient funds is different from a declined card — while framework errors should typically escalate to a centralized recovery path.

## Four Calling Conventions

### 1. `zart::require()` — Fail-Fast (the Default)

The most common path. Any non-`Ok` outcome (business or framework error) fails the entire execution.

<Tabs syncKey="sdk">
<TabItem label="Rust">

```rust
let inventory = reserve_inventory(order_id.clone()).await?;
// ──────────────────────────────────────────────────────────────
// If reserve_inventory returns BusinessErr or ZartErr,
// the execution fails immediately with TaskError::StepFailed.
```

</TabItem>
<TabItem label="Python">

```python
# Direct await uses require() semantics — raises on any error
inventory = await reserve_inventory(order_id)
```

</TabItem>
<TabItem label="TypeScript">

```ts
// Direct yield* uses require() semantics — fails the workflow Effect on any error
const inventory = yield* reserveInventory(orderId);
```

</TabItem>
</Tabs>

Use `require` when a step's failure means the whole workflow cannot proceed.

### 2. `step()` / `Zart.outcome()` — Explicit Three-Way Matching

When the body genuinely needs to branch on a step's specific business error, use `zart::step()` (Rust/Python) or `Zart.outcome()` (TypeScript) to inspect `StepOutcome`.

<Tabs syncKey="sdk">
<TabItem label="Rust">

```rust
use zart::error::StepOutcome;

let balance = match zart::step(check_balance(account_id.clone())).await? {
    StepOutcome::Ok(b) => {
        println!("Balance: ${}", b);
        b
    }
    StepOutcome::BusinessErr(PaymentError::InsufficientFunds { balance, needed }) => {
        return Ok(OrderOutput {
            status: "insufficient_funds".into(),
            message: format!("Have ${}, need ${}", balance, needed),
            // ...
        });
    }
    StepOutcome::BusinessErr(PaymentError::CardDeclined { reason }) => {
        return Ok(OrderOutput {
            status: "card_declined".into(),
            message: format!("Card declined: {}", reason),
            // ...
        });
    }
    StepOutcome::ZartErr(e) => return Err(e.into()),  // escalate to on_failure
};
```

</TabItem>
<TabItem label="Python">

```python
outcome = await zart.step(check_balance(account_id))
if outcome.is_ok:
    balance = outcome.value
    print(f"Balance: ${balance}")
elif outcome.is_business_err:
    return OrderOutput(status="payment_error", message=str(outcome.error))
else:
    raise outcome.error  # escalate ZartErr to on_failure
```

</TabItem>
<TabItem label="TypeScript">

```ts
const balanceOutcome = yield* Zart.outcome(checkBalance(accountId));
if (balanceOutcome._tag === "business_err") {
  return { status: "payment_error", message: balanceOutcome.message };
}
if (balanceOutcome._tag === "zart_err") {
  return yield* Effect.fail(balanceOutcome.error);
}
const balance = balanceOutcome.value;
```

</TabItem>
</Tabs>

The outer `?` (in Rust) propagates control-flow signals (`Scheduled`, `StepExecuted`) — these are framework internals, never matched by user code. The `StepOutcome` is what you actually branch on.

### 3. `step_or()` / `Zart.stepOr()` — Blind Fallback

Discard any error and return a default value. Use only when the failure reason doesn't matter.

<Tabs syncKey="sdk">
<TabItem label="Rust">

```rust
let cached_config = zart::step_or(
    fetch_remote_config(),
    Config::default(),
).await?;
```

</TabItem>
<TabItem label="Python">

```python
cached_config = await zart.step_or(fetch_remote_config(), default_config)
```

</TabItem>
<TabItem label="TypeScript">

```ts
const cachedConfig = yield* Zart.stepOr(fetchRemoteConfig(), defaultConfig);
```

</TabItem>
</Tabs>

### 4. `step_or_else()` / `Zart.stepOrElse()` — Computed Fallback

The closure receives the step's business error — framework errors (`ZartErr` / `ZartTaggedError`) still propagate and are not silently swallowed.

<Tabs syncKey="sdk">
<TabItem label="Rust">

```rust
let payment = zart::step_or_else(
    charge_card(account_id.clone(), data.amount),
    |e: PaymentError| {
        println!("Payment fallback: {}", e);
        PaymentResult { transaction_id: "fallback".into(), amount: 0.0 }
    },
)
.await?;
```

</TabItem>
<TabItem label="Python">

```python
payment = await zart.step_or_else(
    charge_card(account_id, data.amount),
    lambda err: PaymentResult(transaction_id="fallback", amount=0.0),
)
```

</TabItem>
<TabItem label="TypeScript">

```ts
const payment = yield* Zart.stepOrElse(
  chargeCard(accountId, data.amount),
  (_err) => ({ transactionId: "fallback", amount: 0 }),
);
```

</TabItem>
</Tabs>

If `charge_card` returns `BusinessErr(PaymentError::CardDeclined)`, the closure runs. If it returns `ZartErr` (retry exhausted), the error propagates — no silent swallowing.

## Centralized Recovery with `on_failure`

When any propagated failure reaches the top of the workflow, the `on_failure` handler (Rust/Python) or `onFailure` option (TypeScript) is invoked.

<Tabs syncKey="sdk">
<TabItem label="Rust">

```rust
#[zart_durable("order-processing", on_failure = handle_order_failure)]
async fn process_order(data: OrderInput) -> Result<OrderOutput, TaskError> {
    let inventory = reserve_inventory(data.order_id.clone()).await?;
    let payment = charge_card(data.account_id.clone(), data.amount).await?;
    // ...
}

async fn handle_order_failure(
    data: OrderInput,
    failure: ExecutionFailure,
) -> Result<OrderOutput, TaskError> {
    match failure {
        ExecutionFailure::StepFailed { step, raw } if step == "charge-card" => {
            // Deserialize raw back into the step's typed error
            match serde_json::from_value::<PaymentError>(raw.clone()) {
                Ok(PaymentError::InsufficientFunds { balance, needed }) => {
                    Ok(OrderOutput {
                        status: "payment_failed".into(),
                        message: format!("Insufficient funds: have ${}, need ${}", balance, needed),
                        // ...
                    })
                }
                Ok(PaymentError::CardDeclined { reason }) => {
                    Ok(OrderOutput {
                        status: "payment_failed".into(),
                        message: format!("Card declined: {}", reason),
                        // ...
                    })
                }
                Err(_) => {
                    // Framework error — raw may not be a PaymentError
                    Ok(OrderOutput {
                        status: "payment_failed".into(),
                        message: format!("Payment step failed: {}", raw),
                        // ...
                    })
                }
            }
        }
        ExecutionFailure::ExecutionDeadlineExceeded => {
            Ok(OrderOutput { status: "timed_out".into(), /* ... */ })
        }
        ExecutionFailure::RetriesExhausted { attempts } => {
            Ok(OrderOutput {
                status: "retries_exhausted".into(),
                message: format!("Gave up after {} attempts", attempts),
                // ...
            })
        }
    }
}
```

</TabItem>
<TabItem label="Python">

```python
async def handle_order_failure(
    _data: OrderInput,
    failure: zart.ExecutionFailure,
) -> OrderOutput:
    if failure.kind == "step_failed" and failure.step == "charge-card":
        return OrderOutput(status="payment_failed", message=f"Payment failed: {failure.raw}")
    if failure.kind == "execution_deadline_exceeded":
        return OrderOutput(status="timed_out", message="Execution deadline exceeded")
    if failure.kind == "retries_exhausted":
        return OrderOutput(status="retries_exhausted", message=f"Gave up after {failure.attempts} attempts")
    raise RuntimeError(f"Unhandled failure: {failure}")

@zart.durable("order-processing", on_failure=handle_order_failure)
async def process_order(data: OrderInput) -> OrderOutput:
    inventory = await reserve_inventory(data.order_id)
    payment = await charge_card(data.account_id, data.amount)
    return OrderOutput(status="completed", message="ok")
```

</TabItem>
<TabItem label="TypeScript">

```ts
const processOrder = Zart.durable(
  "order-processing",
  (data: OrderInput) =>
    Effect.gen(function* () {
      const inventory = yield* reserveInventory(data.orderId);
      const payment = yield* chargeCard(data.accountId, data.amount);
      return { status: "completed", message: `charged ${payment.transactionId}` };
    }),
  {
    onFailure: (_data, failure) => {
      if (failure.kind === "step_failed" && failure.step === "charge-card") {
        return Effect.succeed({
          status: "payment_failed",
          message: `Payment failed: ${JSON.stringify(failure.raw)}`,
        });
      }
      if (failure.kind === "execution_deadline_exceeded") {
        return Effect.succeed({
          status: "timed_out",
          message: "Execution deadline exceeded",
        });
      }
      if (failure.kind === "retries_exhausted") {
        return Effect.succeed({
          status: "retries_exhausted",
          message: `Gave up after ${failure.attempts} attempts`,
        });
      }
      return Effect.succeed({
        status: "failed",
        message: `Step ${failure.step} failed`,
      });
    },
  },
);
```

</TabItem>
</Tabs>

### `ExecutionFailure` Variants

| Variant | Meaning |
|---|---|
| `StepFailed { step, raw }` | A step returned a non-Ok outcome that propagated to the top. `raw` is the JSON-serialized error. |
| `ExecutionDeadlineExceeded` | The execution-level timeout (`timeout = "30m"`) was exceeded. |
| `RetriesExhausted { attempts }` | The execution-level retry policy exhausted all attempts. |

## Error Types at a Glance

| Type | Where it appears | What it means |
|---|---|---|
| `StepOutcome<T, E>` | Return of `zart::step()` | Three-way: Ok / BusinessErr / ZartErr |
| `StepError` | `?` propagation, `zart::wait` element | Control-flow signal or user domain error |
| `TaskError` | Return of `run`, return of `require` | Top-level execution failure |
| `ZartStepError` | Inside `StepOutcome::ZartErr` | Framework failure: retry exhausted, timeout |
| `ExecutionFailure` | Passed to `on_failure` | Why the centralized handler was invoked |

## Choosing a Calling Convention

```
Does the step's failure mean the whole workflow should stop?
├─ Yes → use require()
└─ No → Do you need to branch on specific business errors?
        ├─ Yes → use step() + match StepOutcome
        └─ No → Is a default value always acceptable?
                ├─ Yes → use step_or()
                └─ No → use step_or_else() with a fallback closure
```
